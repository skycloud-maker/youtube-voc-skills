# 감독자 — 두 판독이 갈린 행의 주제를 정한다

두 판독자가 같은 댓글에 **다른 답**을 냈습니다.
원문을 보고 **어느 쪽이 맞는지, 아니면 둘 다 아닌지** 정하십시오.

```
  ★ 어떤 제품군인지는 데이터가 정한다. 미리 정해 두지 마라.
    한 판에 여러 제품군이 섞여 있는 것이 보통이다 —

  ★★ **경쟁사 얘기도 분석 대상이다.** 빼지 마라.
```

## 판정

행마다 셋 중 하나입니다.

```
A        A 가 맞다
B        B 가 맞다
C        ★ 둘 다 아니다 — 당신이 답을 낸다
D        ★★ 둘 다 맞다 — 한 행에 주제가 여럿이라 **나눠야 한다**
```

`C`·`D` 를 낼 때만 **왜 그렇게 봤는지 한 줄**을 적습니다. `A`·`B` 는 이유가 필요 없습니다.

### ★★ `D` — 나눠야 하는 행

A 와 B 가 **둘 다 맞을 때**가 있습니다. 한 문장에 서로 다른 대상이 둘 있어서입니다.

```
「아무리이쁘고 히든스테이션이래도 외출중 청소기가꼇습니다.
  물걸레패드가빠졌습니다. 이딴알람오면 개빡친다」
   → A 물걸레 · B 에러/오작동 — 둘 다 맞다. 나눠야 한다
```

★ 예전에는 이걸 말할 칸이 없어서 억지로 하나를 골랐고, 그래서 갈렸고,
  사람에게 넘어갔습니다. **4차에서 69행 중 11행이 이것이었습니다.**

★ 다만 **원인을 주제로 삼지 마십시오** (기준서 §8).
  「스팀 때문에 곰팡이 생김」 은 둘이 아니라 하나입니다 —
  향하는 대상은 곰팡이고 스팀은 원인입니다. 가름법은 이렇습니다.

```
빼고 읽어도 불만이 남는가
   「스팀 때문에」 를 빼도 「곰팡이 생김」 은 남는다  → 하나 (위생/냄새)
   「물걸레패드가빠졌습니다」 를 빼도 「청소기가꼇습니다」 는 남는다  → 둘
```

★ `이_원문의_조각수` 가 **1** 인데 주제가 여럿이면 과소분리입니다.
  **여럿**인데 조각들이 같은 대상을 말하면 과분리입니다 — 그것도 `D` 로 알려 주십시오.

### ★★ 조각은 원래 글을 **빠짐없이** 덮어야 합니다  (2차 계약 L-3)

```
Sum(조각의 atomic_voc)  +  남는 글  =  원래 행의 atomic_voc
```

조각은 **대표 문장을 오려 내는 것이 아닙니다.** 글을 나누는 것입니다.
어느 조각에도 안 들어간 글은 **데이터에서 사라집니다.**

* 조각들을 원문 순서대로 이어 붙이면 원래 `atomic_voc` 가 나와야 합니다
* 어느 주제에도 안 들어가는 나머지(인사말·감탄사 등)가 있으면
  `"residual"` 에 적어 주십시오. 버리지 마십시오
* 판단이 서지 않는 글은 **가까운 조각에 붙이십시오.** 빼는 것보다 낫습니다

> ★ 왜 — 실제로 이런 일이 있었습니다.
> 「정수통이랑 오수통까지 안쪽에 숨겨지는 구조라」 「카메라 보안을 자동 도어로
> 물리적으로 막아주는 디테일도 믿음이 갔어요」 가 어느 조각에도 안 들어가
> 사라질 뻔했습니다. 잡담이 아니라 실제 VoC 입니다.

**회차를 끝낼 때 `python 스크립트\조각덮개검사.py` 를 돌리십시오.**
덮개율이 낮은 행을 짚어 줍니다.

★ `D` 의 `segments` 는 **원문 안의 연속된 부분**이어야 합니다.
  요약하거나 고쳐 쓰지 마십시오 — 원문에서 그대로 오려 냅니다.
  총괄이 기계로 검사합니다. 어긋나면 통째로 되돌아옵니다.

**모든 행에 답을 내십시오.** 「모르겠다」 는 아래 확인 요청으로만 냅니다.
행 수는 `judge_input.csv` 를 세어 보면 된다. 578 로 외우지 마라.

```
판독패키지\8_topic_그룹.md           라벨 묶음
```

**`9_택소노미_2차확장.md` 를 먼저 통째로 읽으십시오.**
여기에 지난 판에서 사람이 정한 규칙이 다 있습니다 —
원산지·OEM(§7) · 안전·위생(§8) · 위생 이름 통일(§9) · 짧은 경쟁 비교(§10) ·
PL(§11) · 출시/출시일정(§12) · 라벨 신설(§13) · 긍정 나열(§14) · 「분리」의 두 뜻(§15).

> ★ 지난 판에 이 문서가 폴더에 **있었는데도** 반영되지 않았습니다.
> 프롬프트가 「읽으십시오」 라고 말하지 않았기 때문입니다.
> §9(위생 이름 통일)·§12(출시) 가 데이터에 하나도 들어오지 않았습니다.
> **폴더에 있다고 읽히지 않습니다.**

이미 정해진 규칙으로 풀리는 갈림을 다시 갈리게 두지 마십시오.
A·B 중 어느 쪽도 규칙에 맞지 않으면 `C` 로 직접 내십시오.

## 이 행이 왜 왔는가 — `갈래` 를 먼저 보십시오

이번 판부터 **네 갈래**가 옵니다. 갈래마다 묻는 것이 다릅니다.
`judge_input.csv` 의 `갈래` · `물음` 칸에 적혀 있습니다.

| 갈래 | 무엇을 묻는가 | 낼 답 |
|---|---|---|
| ① 라벨이 다름 | 두 판독자가 다른 라벨을 달았다 | `A` · `B` · `C` · `D` |
| ② 한쪽 라벨 · 한쪽 제외 | 한쪽은 분석 대상이라 하고 한쪽은 아니라 한다 | `A` · `B` · `C` · `D` |
| ③ 한쪽만 쪼갠 행 | **한쪽만 이 조각을 만들었다** | 아래 참조 |
| ④ 과분리 후보 | 둘 다 합의했지만 한 원문이 여러 조각이다 | 아래 참조 |

### ③ 한쪽만 쪼갠 행

한쪽 판독자가 「여기는 두 주제다」 하고 조각을 만들었고, 다른 쪽은 안 만들었습니다.
한쪽의 답이 `(이 판독자는 이 조각을 만들지 않았습니다)` 로 옵니다.
**「못 골랐다」 가 아니라 「안 만들었다」 입니다.** 다릅니다.

`형제조각` 칸에 같은 원문에서 나온 조각이 전부 들어 있습니다. 그것을 보고 정하십시오.

* 분리가 맞다 → 조각을 만든 쪽 (`A` 또는 `B`) 을 고릅니다
* 분리가 틀렸다 → `D` + `"merge": true` 로 「합쳐야 한다」 고 알립니다
* 나누는 자리가 아예 다르다 → `D` + `segments` 로 옳은 조각을 내십시오

### ④ 과분리 후보 (둘 다 합의)

판독자 둘 다 이대로 두자고 했습니다. 그런데 한 원문이 여러 조각입니다.
**둘 다 합의했다는 것이 옳다는 뜻은 아닙니다.**

> ★ 왜 묻는가 — 지난 판에서 판독자 둘 다 병합을 **한 건도 안 냈습니다.**
> 지시는 있었는데 아무도 안 냈습니다. 아무도 안 보면 영원히 안 보입니다.

* 이대로가 맞다 → `A` 를 고릅니다 (둘의 답이 같으니 어느 쪽이든 같습니다)
* 굳이 나눌 것이 아니었다 → `D` + `"merge": true`

**「합칠 것 없음」 이라고 답하는 것도 결과입니다.** 억지로 합치지 마십시오.

## ★★ `D` 로 조각을 낼 때 — 빈 칸을 전부 채우십시오

조각은 **새 행**입니다. 라벨만 주면 나머지 50여 칸이 부모 값 그대로 복사됩니다.
그러면 「디자인」 조각에 「스팀 성능」 이라는 근본원인이 붙습니다. 실제로 그랬습니다.

**이어받는 19칸** (총괄이 알아서 넘깁니다 — 적지 마십시오)

```
source_id · raw_row_index · parent_voc_id · comment_relation · original_voc ·
voc_cleaned · voc_residual · reference_brand · market · language ·
source_context_summary · status · scope_exclusion_reason · proposal_flag ·
video_id · video_title · video_url · product_category · product_category_source
```

**당신이 채울 것** — 조각마다 새 `atomic_voc` 를 기준으로 다시 판정합니다

```json
{"atomic_id": "...", "verdict": "D",
 "segments": [
   {"atomic_voc": "원문에서 그대로 오려 낸 부분",
    "topic": "에러/오작동", "topic_evidence": "원문 인용",
    "cej": "사용", "cej_evidence": "원문 인용",
    "rootcause_target": "...", "rootcause_cause": "...",
    "rootcause_summary": "...", "rootcause_score": 3,
    "tee_time_score": 0,  "tee_time_evidence": "",
    "tee_effort_score": -2, "tee_effort_evidence": "원문 인용",
    "tee_emotion_score": -3, "tee_emotion_evidence": "원문 인용",
    "tee_success_score": -3, "tee_success_evidence": "원문 인용",
    "tee_summary": "...",
    "inquiry_flag": "N", "inquiry_type": "",
    "need_signal_flag": "Y", "need_signal_type": "...",
    "entity_role": "product_brand", "sentiment_dir": "부정",
    "confidence_topic": "High", "confidence_cej": "Medium",
    "confidence_inquiry": "Low", "confidence_need_signal": "Low",
    "confidence_entity_role": "High", "confidence_score": "High"}
 ],
 "why": "불만이 향하는 대상이 둘이다"}
```

* `rootcause_score` — 문제만 1 · 문제+대상 3 · 문제+대상+원인 5.
  원문에 없는 원인을 지어내지 마십시오. 모르면 1 이나 3 으로 둡니다
* `*_evidence` 는 **원문 인용**입니다. 설명문을 쓰지 마십시오
* Enum 칸(`cej` · `entity_role` · `inquiry_type` · `need_signal_type` ·
  `inquiry_flag` · `need_signal_flag`)은 **공란을 허용하지 않습니다**.
  비우면 최종 번들의 계약 검증이 반려합니다
* `confidence_rating` 은 기계가 계산합니다. 위 6종만 당신이 채웁니다

### 칸에 넣을 값 — **데이터에서 뽑은 실제 값입니다**

```
confidence_* 6종     High · Medium · Low        ★ 숫자가 아닙니다
sentiment_dir        긍정 · 부정 · 중립          ★ 한국어입니다
rootcause_score      0 · 1 · 3 · 5              (0 = 근본원인 없음)
cej                  해당없음 · 탐색 · 인지 · 사용준비 · 사용 · 관리 ·
                     결정 · 구매 · 교체 · 배송
entity_role          product_brand · creator_channel · competitor_brand · unknown
inquiry_flag         Y · N
need_signal_flag     Y · N
inquiry_type         none · other_question · feature_spec · review_request ·
                     product_identification · product_comparison ·
                     usage_environment_fit · installation_fit ·
                     as_trust_quality · purchase_path_link · promotion_benefit
need_signal_type     none · trust_safety_need · problem_solution_need ·
                     content_information_need · conversion_signal ·
                     price_value_need · feature_need · positive_message_candidate ·
                     environment_fit_need · purchase_confidence_need ·
                     purchase_path_need
scope_exclusion_reason
                     no_analytic_value · out_of_scope_product · channel_feedback ·
                     empty · unresolvable_reply · channel_request ·
                     operator_notice · business_signal
```

★ `confidence_*` 를 전부 같은 값으로 채우지 마십시오.
  확신이 낮으면 `Low` 라고 적는 것이 정직합니다. 그 칸은 그러라고 있습니다.



**`"merge": true` 일 때도 같습니다.** 합쳐진 조각을 기준으로 라벨·요약·해석 여지를
다시 판정해 `segments` 에 **한 덩어리로** 적으십시오.

> ★ 이 규칙은 2차 판독이 이미 지키던 것입니다 (2차 확장부록 §2.4).
> 새로 만든 규칙이 아니라, 3차에도 똑같이 적용하는 것입니다.

```
★ 행 단위로 올리지 마십시오. 묶음으로 올립니다
```

```json
{"확인요청": [
```

**「혹시 모르니 다 봐 달라」 는 하지 마십시오.** 많이 올린다는 것은 기준이 없다는 뜻이므로,

## 내는 방식

```
_판독패키지/_결과/감독결과_<회차2자리>_<이름>.md
   이름 = codex 또는 claudecode
```

회차마다 파일을 따로 씁니다.

★ **어디부터 하나** — `_판독패키지/_결과/` 를 먼저 보십시오.
  이미 파일이 있는 회차는 끝난 것입니다. **없는 회차부터** 하면 됩니다.
  비어 있으면 처음부터 합니다. 사람에게 묻지 마십시오.

★ 파일 머리에 그 회차를 **실제로** 시작한 시각과 끝낸 시각을 적는다.
  나중에 몰아서 적지 마라. 시작과 종료가 같으면 반려다.

★★ 회차를 마칠 때마다 성실성 검사를 돌린다

    python 스크립트\성실성검사.py "<방금 쓴 판정 파일>"
    python 스크립트\지문검사.py

  ★★★ 성실성 검사에는 **방금 쓴 파일 하나만** 준다.
    인자 없이 돌리면 폴더 전체를 봐서, 아직 안 한 회차까지 반려로 나온다.
    그러면 잘했는데도 다음으로 못 간다.

  「반려」 가 나오면 다음 회차로 가지 말고 그 회차를 다시 한다.

## ★ 마지막 회차를 마친 뒤에 하는 것

★★ **「내가 마지막인가」 는 세어 보면 안다.** 사람에게 묻지 마라.

```
  s13_judge\judge_*_ids.txt 개수  =  _판독패키지\_결과\감독결과_*.md 개수
```

두 수가 같으면 아래를 한다. 모자라면 「judge_NN 까지 했습니다」 만 알리고 멈춘다.

```
  (1) 스스로 성실성을 본다 — 반려가 나오면 그 회차만 다시 한다
      python 스크립트\성실성검사.py

  (2) 도구·기준이 안 바뀌었는지 본다
      python 스크립트\지문검사.py

  (3) 넘어가도 되는지 스스로 판단한다
      python 스크립트\넘어가도_되나.py
```

★★ **통합은 총괄이 합니다. 네가 하지 않는다.**

  다른 감독자의 결과를 **찾지도, 가져오지도 마라.**
  감독 폴더는 한 사람 것만 있어야 한다 —
  남의 결과가 섞이면 누가 무엇을 했는지 알 수 없게 된다.

  총괄이 두 폴더를 받아 자기 자리에서 합칩니다.

★ 다 끝나면 사람에게 이렇게만 알린다

```
  감독자를 마쳤습니다. 회차 <N>개 · <행수>행.
  성실성검사 · 지문검사 · 넘어가도_되나 모두 통과했습니다.

  결과는 이 폴더의 `_판독패키지\_결과\감독결과_*.md` 에 있습니다.
  이 폴더를 총괄께 그대로 넘겨 주십시오.
```

★ 「확인 요청」 과 「담을 라벨이 없다」 는 네가 고치는 것이 아니다.
  판정 파일에 적어 두면 총괄이 논의본으로 옮긴다.
