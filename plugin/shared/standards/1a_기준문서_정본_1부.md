## 0-1. 【v4.3 신설】 필수 첨부 문서 세트 — 이 문서 하나로는 검수가 안 된다

배경 — 식기세척기 7차 재분석을 외부 LLM(ChatGPT)에 이 기준문서만 첨부해 검수를 맡긴 결과, "위생/살균"를 존재하지도 않는 비허용 topic 라벨이라고 오판하는 사고가 발생했다(2026-08-09). 원인은 이 기준문서가 판정 규칙(R1~R17)과 필드별 점검 기준은 담고 있지만, topic 허용 라벨의 전체 목록(택소노미)과 컬럼별 enum 허용값 전체 목록(데이터사전)은 요약·발췌 수준으로만 인용하고 원본을 담고 있지 않기 때문이다. 검수자가 이 두 원본 문서를 같이 받지 못하면, 그럴듯해 보이는 값도 실제로는 정상인지 오류인지 판단할 근거가 없어 추측으로 판정하게 된다.
이 문서로 검수를 요청할 때는 아래 4개 문서를 항상 함께 첨부한다. 누락하면 검수자가 허용값을 확인할 방법이 없어 오탐/누락이 발생한다.
① 이 기준문서(23_VoC_결과파일_점검_기준문서, 최신 버전) — 판정 절차·R1~R17 규칙
② VoC Topic 택소노미 재설계 문서(현재 v0.7) — topic 허용 라벨 전체 목록과 제품군별 근거 어휘. 이게 없으면 "이 topic 라벨이 허용값인지" 자체를 판단할 수 없다.
③ VoC 데이터 사전(스키마) 최신본(현재 v2.8) — 특히 '값 목록(Enum)' 시트. inquiry_type·need_signal_type·cej·entity_role 등 컬럼별 허용값 전체 목록. 이게 없으면 "이 값이 허용값 밖인지" 자체를 판단할 수 없다.
④ VoC 분석 엔진 재현 설계서 최신본(현재 v10) — 판정 로직이 왜 그렇게 동작하는지의 근거. 필수는 아니지만, 근거(evidence)와 판정값이 서로 모순돼 보일 때 "엔진이 원래 이렇게 설계됐다"인지 "엔진 버그"인지 구분하려면 있는 것이 좋다.
이 네 문서의 최신 버전은 repo `docs/cowork/handoff-current/`에서 관리한다(파일명 번호 접두사는 README 참조). 검수를 GitHub 링크 접근이 가능한 도구(Codex 등)에 맡길 때는 이 경로를 알려주고 "최신 버전을 확인해서 사용하라"고 명시한다. 링크 접근이 불가능한 도구(예: 일반 ChatGPT 채팅)에 맡길 때는 위 4개 파일을 반드시 직접 첨부한다 — 문서 존재를 안내하는 것만으로는 검수자가 실제로 열어볼 수 없으므로 부족하다.
주의 — 첨부가 불가능하거나 빠뜨렸다면, 검수를 시작하기 전에 그 사실을 먼저 보고하고 "택소노미/데이터사전 원본 없이 허용값을 요약 기억에 의존해 판정했다"는 한계를 결과에 명시하도록 요청 문구에 포함시킨다(§1 표준 프롬프트에 반영됨).

## 0-2. 【v4.4 신설】 검수 시 "N/A" 판독 함정 — 빈칸이 아닌데 빈칸으로 오판하지 말 것

topic·rootcause_* 등 필드에 엔진이 정상적으로 문자열 "N/A"를 채워 넣었더라도, 결과 파일을 pandas(Python) 등으로 읽을 때 기본 설정으로는 "N/A"·"NA"·"null" 같은 문자열이 자동으로 결측치(NaN)로 변환된다. 이 상태로 topic 값을 점검하면 정상적으로 N/A가 채워진 행이 "빈칸(공란) 오류"로 잘못 보고된다. 2026-08-10 다중 제품군 첫 실분석 QA에서 실제로 이 함정에 걸려 "topic 공란 490건"을 구조적 결함으로 오판했으나, keep_default_na=False 옵션으로 다시 읽자 실제 빈칸은 0건임이 확인됐다. 결과 파일을 코드로 읽어 점검할 때는 반드시 pandas.read_csv/read_excel에 keep_default_na=False, na_values=[] 옵션을 주거나, 최소한 "topic이 NaN인 행"과 "topic 셀 문자열이 실제로 비어 있는 행"을 구분해서 봐야 한다. 사람이 엑셀 뷰어로 셀을 직접 열어 눈으로 확인하는 것이 가장 확실하다.

## 1. 【맨 앞】 LLM에 붙여 쓰는 표준 요청 프롬프트

아래 블록을 그대로 복사해서, 분석 결과 파일 + 이 기준 문서와 함께 채팅에 붙인다.
당신은 가전제품 회사의 VoC(Voice of Customer) 전문 분석가입니다.첨부한 VoC 1차 분석 결과 파일을, 함께 첨부한 「VoC 결과파일 점검 기준 문서」에 따라검수해 주세요.[검수 시작 전 확인]아래 4개 문서가 모두 첨부되어 있는지 먼저 확인하세요: ①이 기준문서 ②VoC Topic 택소노미 재설계 문서 ③VoC 데이터 사전(스키마) — 특히 '값 목록(Enum)' 시트 ④VoC 분석 엔진 재현 설계서(선택, 있으면 사용).②·③ 중 하나라도 빠져 있으면, topic 라벨이나 컬럼 값이 허용값인지 원본으로 확인할 수 없습니다. 이 경우 검수를 진행하되, 결과 맨 앞에 "택소노미/데이터사전 원본 없이 진행함 — 허용값 판정은 기억·추정에 의존했으므로 신뢰도 낮음"이라고 반드시 먼저 밝히세요. 짐작으로 "허용값 위반"이라고 단정하지 마세요.[0단계 — 전제 점검 (반드시 먼저)]개별 행을 보기 전에, 아래 3가지를 먼저 확인하고 결과를 알려주세요. (1) source_context_summary 에 keyword= 또는 product= 같은 실행 힌트가 섞여 있는가?     → 있으면 product_category 판정 전체가 오염됐을 수 있으므로 그 사실을 먼저 보고. (2) comment_relation=reply 인 행의 컨텍스트에 parent_voc= 가 들어있는가?     → 없으면 답글 행은 부모 없이 판정된 것이므로 그 사실을 먼저 보고. (3) trace_summary 에 override / guard 흔적이 있는가? 있으면 종류와 건수를 집계.[1단계 — Atomic 분리 점검]분석 결과 컬럼을 먼저 보지 말고, original_voc(원문 댓글)만 먼저 읽으세요.그 댓글 안에 독립적으로 분석될 수 있는 의미 단위가 몇 개인지 스스로 먼저 판단한 뒤,atomic_voc(실제 분리 결과)와 비교하세요. - 분리 누락 / 과도 분리 / 의미 손실·주입 / 발췌가 아닌 요약 - 분리된 atomic들이 서로 같은 topic을 공유하고 있지 않은가 (재판정 누락 신호)[2단계 — 필드 점검]각 atomic_voc 를 기준으로 아래를 점검하세요. topic / product_category(+source) / cej / inquiry_flag·type / need_signal_flag·type / entity_role / tee_*_score / rootcause_* / confidence_*[3단계 — 정합성 점검]한 행 안의 필드들이 서로 모순되지 않는지, 근거(evidence)가 결론을 뒷받침하는지 확인하세요.[판단 원칙]- 판단 단위는 original_voc가 아니라 atomic_voc입니다. 단, 1단계에서만 original_voc 기준입니다.- 기준 문서의 허용값 밖의 값이 있으면 그 자체가 오류입니다.- topic은 그 라벨의 근거 어휘가 원문에 실제로 있어야 배정할 수 있습니다(R13).- Root Cause는 결핍 서술이 있을 때만 부여합니다(R14).- 기준 문서에 없는 유형이라도 원문을 읽었을 때 이상하면 반드시 지적하세요.- 확실한 근거가 없으면 "오류"로 단정하지 말고 "재검토 필요"로 분류하세요.[출력 형식]발견 항목마다 표로 정리해 주세요. source_id / atomic_id / original_voc(필요 부분) / atomic_voc / 문제 필드와 현재 값 / 왜 이상한지(어느 원칙·규칙 위반인지 명시) / 근거 문장 / 제안값(A→B, 확신 없으면 "재검토 필요") / 판정 구분: [오류] / [재검토 필요] / [기준서 미커버] / 오류 유형: Atomic 분리 / Topic / product_category / CEJ / Inquiry / Need /            Entity Role / TEE·S / Root Cause / Confidence / 근거-결론 불일치마지막에 요약: 검토 행 수, 판정 구분별 건수, 반복 오류 유형 3가지,"기준 문서로는 판단할 수 없었던 항목" 목록, 그리고 0단계 전제 점검 결과.
대량 파일일 때: video_id 단위 또는 200~300행 단위로 나눠 여러 번 요청하고, 회차마다 위 프롬프트를 그대로 재사용한다. 단 0단계 전제 점검은 첫 회차에 한 번만 하면 된다.

## 2. 이 문서를 쓰는 이유

1차 분석 결과를 자동으로 재검증하는 시스템(QC-REVIEW-01)을 구축하려 했으나, LLM 기반 검증 레이어도 1차 엔진과 동일한 LLM 비결정성의 한계를 벗어나지 못한다는 게 확인되어 자동화는 보류했다. 대신 실무자가 그때그때 결과 파일을 LLM 채팅에 직접 주고 물어보는 방식이 더 빠르고 유연하다고 판단했다. 다만 매번 무엇을 봐달라고 할지 즉흥적으로 설명하면 점검 품질이 들쭉날쭉해지므로, 지금까지 실제로 발견됐던 오류 패턴과 판단 기준을 정리해 표준 요청 문구로 쓸 수 있게 만든 것이 이 문서다.
v4.0에서 판단 근거(택소노미·허용값·판정 규칙)를 문서 안으로 가져왔고, v4.1에서는 실제로 한 번 돌려본 결과를 반영했다. 그 과정에서 얻은 가장 큰 교훈은 이것이다.
개별 판정을 보기 전에 엔진이 무엇을 보고 판단했는지부터 확인해야 한다. Round 1에서 topic 오류 수십 건을 잡았지만, 그 절대다수는 개별 판정 실수가 아니라 ①topic이 atomic별로 재판정되지 않은 구조 ②실행 힌트가 컨텍스트를 오염시킨 것 ③부모 댓글이 아예 주입되지 않은 것에서 파생된 것이었다. 전제를 모르면 증상만 100건 적어내게 된다.
동시에 이 문서의 성격은 여전히 “규정집”이 아니라 “LLM이 스스로 의심하게 만드는 문서”다. 규칙을 늘리는 것보다 “이런 실수를 하기 쉽다”를 보여주는 쪽이 LLM의 행동을 훨씬 잘 유도한다.

## 3. 요청 시 사용법

결과 파일과 이 문서를 함께 채팅에 첨부하고 §1의 표준 프롬프트를 붙여넣는다. 짧게 쓰고 싶다면 최소한 다음은 반드시 포함한다.
“첨부한 VoC 분석 결과 파일을, 첨부한 점검 기준 문서에 따라 검수해줘. 먼저 컨텍스트에 실행 힌트가 섞였는지, 답글에 부모가 주입됐는지 전제부터 확인하고, 그 다음 original_voc만 읽고 의미 단위를 스스로 판단한 뒤 atomic 분리가 맞는지 보고, 마지막으로 각 atomic 기준으로 필드를 점검해줘. 확신 없으면 오류로 단정하지 말고 ’재검토 필요’로 표시해줘.”
“원문과 대조해서 봐줘”만 요청하면 LLM이 original_voc를 판단 단위로 착각한다. 실제 판단 단위는 atomic_voc이고, original_voc는 분리 적정성을 볼 때만 기준이 된다.

## 4. 점검 전에 알아야 할 것


### 4.1 텍스트가 3층으로 되어 있다


| 컬럼 | 무엇인가 | 점검 포인트 |
|---|---|---|
| original_voc | 원문 댓글 그대로 | 판단의 최종 근거. 여기 없는 의미가 뒤 컬럼에 있으면 오류 |
| voc_cleaned | NFC·제어문자·공백만 정리한 source 정제 원문 | 이모지·반복부호·@호출명·인사말이 원형 보존되는지 확인 |
| atomic_voc | 독립 분석 단위. voc_cleaned에서 발췌한 텍스트 | 요약·의역이면 오류. 정제되지 않은 원문 문자열이 그대로 들어와도 규격 이탈 |
| voc_residual | 어느 atomic_voc에도 포함되지 않은 미사용 span | 형제 전원 동일하며 원문 순서대로 보존되는지 확인 |

atomic_id는 source_id-01, -02 형식이고 분리 개수 상한은 없다. 분리되지 않았으면 atomic_voc는 voc_cleaned와 같다.

### 4.2 판단은 1·2·3차 순서로 내려간다

모든 필드는 ①원문(atomic) → ②parent 댓글 → ③영상(제목/태그/설명) 순서로 판단하고, 앞 단계에서 판단되면 멈춘다. 그래서 “원문에 근거가 없는데 값이 채워져 있다”고 바로 단정하면 안 된다. 2·3차 폴백으로 채워졌을 수 있다. product_category는 어느 단계에서 확정됐는지가 product_category_source(text / parent / video)에 남는다.
단, 실행 힌트(검색 키워드·제품 힌트)는 판단 근거가 아니다. §4.4에서 이것부터 확인한다.

### 4.3 극성은 자사(LG) 관점으로 정규화된다

reference_brand는 LG 고정이다. “삼성이 더 싸더라”는 자사 관점에서 가격 열위(부정 신호)로 기록되는 것이 정상이다. 단, TEE 점수는 “논의 대상 엔티티의 고객 경험”을 반영하므로 경쟁사 부정 경험은 음수로 유지된다(R6). 이 둘을 혼동해 “왜 경쟁사 칭찬이 부정인가”를 오류로 잡으면 오탐이다.

## 6. 판단 대전제

아래 나열되지 않은 새로운 유형의 오류라도 원문을 읽었을 때 “이 판정이 이상하다”고 합리적으로 판단되면 반드시 지적할 것 — 목록에 없다는 이유로 넘어가지 말 것.
판단 단위는 atomic_voc다. 단, atomic 분리 자체가 맞는지는 original_voc 기준으로 먼저 본다. 분리가 틀리면 그 아래 모든 필드가 연쇄적으로 틀린다.
topic은 발화의 핵심 서사를 반영해야 한다. 여러 요소가 섞여 있으면 무엇이 핵심 서사이고 무엇이 부차적 조건·수식절인지 구분한다.
topic은 그 라벨의 근거 어휘가 원문에 실제로 존재해야 배정할 수 있다(R13). “문맥상 그럴 것 같아서” 배정하는 것이 가장 흔한 오류다.
topic은 원문에 등장한 구체적 대상의 세분화 수준을 반영해야 한다. 구체 대상이 명시됐는데 “제품 전반”으로 뭉갰다면 세분화 실패다.
독립된 의도가 둘 이상이면 하나로 압축하지 않는다. 대표 하나를 고르는 것이 아니라 atomic으로 분리해 둘 다 보존한다. 반대로 “문장이 여럿”이라는 이유만으로 한 의도를 쪼개는 것도 오류다.
분리된 atomic이 서로 같은 topic을 공유하면 재판정 누락을 의심한다(R12).
Root Cause는 결핍 서술이 있을 때만 부여한다(R14). 순수 문의·순수 긍정·구매 의사·근거 없는 단답에 문제를 만들어내면 안 된다.
rootcause / entity_role 등도 원문에서 실제로 도출 가능한 근거에 기반해야 하며, 근거 문장이 결론과 논리적으로 일치해야 한다.
confidence는 정보 충족도에 비례해야 한다. 단, 정확도 지표가 아니다(§7.10).
evidence는 실제로 원문에서 인용 가능한 문장이어야 한다.
근거가 없으면 억지로 값을 만들지 않는 것이 정상이다. N/A·미분류·해당없음·unknown은 회피가 아니라 규정된 정답일 수 있다.

## 7. 필드별 판단 기준


### 7.0 Atomic 분리 (1순위)

기준. 분리 기준은 “문장이 여럿이라서”가 아니라 “독립적인 분석 결과(Topic·Inquiry·Need 또는 TEE/S·Root Cause)가 도출될 때만”이다. 독립 결과가 하나면 분리하지 않고, 여럿이면 01, 02, 03 … 순차 번호를 부여한다(상한 없음).
미분리가 맞는 예 - “60만원 이하 입문기 갈까요? 걸레 빠는 것 지쳐요.. 고양이 3마리, 강화마루” → 전부 ‘추천 요청’ 한 의도의 조건. 단일 atomic - “에코백스 x11은 어떤가요, 하이마트 89만원이던데” → 가격+성능이 결합된 ‘가성비 문의’ 하나. 단일 atomic(R9) - “로보락·LG·삼성 중 시공매트 집에 뭐가 좋을까요” → 3사 비교 추천이라는 단일 의도
분리가 맞는 예 - “…중국 ODM/JDM이라 하기 애매 // 이런 정보도 알려주세요” → 01=신뢰 우려, 02=정보 요청 - (v4.1 신설 예문) raw 50 — “플래그쉽에 다 들어있는 스테이션 내부 걸레판 자동 청소 기능이 빠진 건 아쉽네요.. 배터리도.. 스팀청소는 방 한 개? 이건 좀.. 그리고 다음 세대는 걸레가 팔처럼 쭉 뻗어나오는데.. 트렌드에 뒤쳐짐.. 등판 능력은 말할 것도 없고” → 독립 의도 4개: ①걸레판 자동청소 기능 누락 ②배터리 제약으로 스팀 커버리지 부족 ③물걸레 방식의 세대 격차 ④등판 능력 불만. ①과 ③은 둘 다 물걸레 계열이지만 ’기존 기능 누락’과 ’신규 기능 트렌드’로 성격이 달라 병합하지 않는다. 실제 산출물은 이를 단일 atomic + topic=배터리 하나로 처리했다 — 분리 누락의 대표 사례.
점검 시 볼 것 1. 분리 누락 — 독립 결과가 둘 이상인데 하나로 묶였나? (역방향 체크: 이 atomic 하나에서 서로 다른 topic 라벨이 2개 이상 도출 가능한가? 그렇다면 덜 쪼갠 것이다) 2. 과도 분리 — 한 의도의 조건절이 별도 atomic으로 떨어졌나? 3. 발췌 위반 — atomic_voc가 voc_cleaned 발췌가 아니라 요약·의역인가? 정제 전 문자열(“ㅋㅋ”, “~”, “???”)이 잔존하는가? 4. 의미 주입 — 원문에 없는 단어가 들어갔나? 5. 독립 판정 — 분리된 atomic이 각각 독립 점수·판정을 받았나(R3)? 6. 【v4.1】 재판정 누락 — 분리된 atomic들이 모두 같은 topic인가? 그렇다면 원문 단위 topic이 복제된 것이다(R12).

### 7.3 cej — 고객 여정 단계

허용값 (9 + 1): 인지 · 탐색 · 결정 · 구매 · 배송 · 사용준비 · 사용 · 관리 · 교체, 해당 없으면 해당없음. 설치, 구매결정, 유지관리, 이탈 등은 허용값 위반이다. 설치는 사용준비로 매핑한다.
R11 — 가장 많이 틀리는 지점 > CEJ는 이 VoC의 이슈/경험이 속한 여정 단계, 즉 개선이 이뤄질 단계를 가리킨다. 작성자가 지금 쇼핑 여정의 어디에 있는지가 아니다.
【v4.1 신설】 R15 — 사용 vs 사용준비 경계 규칙

| 단계 | 정의 | 예 |
|---|---|---|
| 사용준비 | 제품을 쓸 수 있는 상태로 만드는 과정의 이슈 — 설치 가능 여부, 설치 환경 제약, 배치, 초기 설정 | “y자 배수구 있으면 설치 불가인가요?” · “걸레받이 10cm인데 15cm만 되나요?” · “사무실은 설치 거부당했습니다” |
| 사용 | 설치가 끝난 뒤 제품이 동작하는 중 발생하는 이슈 — 성능, 주행, 청소 결과, 앱 조작 | “문턱은 잘 넘나요?” · “매트 위에 흠집 나요” · “매핑을 매번 새로 함” |

판정 문장: “이 이슈를 해결하려면 설치 사양·정책을 바꿔야 하는가(→사용준비), 제품 동작·성능을 바꿔야 하는가(→사용)?”
v4.1 오탐 기록 — Round 1 검수에서 검수자(LLM)가 “문턱은 잘 넘나요?”를 “구매 전 문의이므로 탐색/결정이 맞다”고 지적했으나, 이것은 R11 위반이며 사용이 정답이다. 문턱 돌파는 제품이 동작하는 중 발생하는 이슈이고, 개선이 이뤄질 단계도 사용이다. 작성자의 현재 위치로 CEJ를 판단하려는 유혹이 검수 측에도 똑같이 작동한다는 것을 보여주는 사례라 기록으로 남긴다.
추가 점검: 사용준비가 0건이면 배정 규칙 자체를 의심한다. Round 1에서 설치 관련 발화가 49건인데 사용준비 0건이었다.

### 7.7 TEE/S

각 축은 −5 · −3 · −1 · 0 · +1 · +3 · +5, 0 = 언급 없음. 각 축에 _evidence가 있어야 한다.

| 축 | 무엇을 보나 | 음수 예 | 양수 예 |
|---|---|---|---|
| Time | 시간·처리속도·대기·소요 시간 | “연결이 오래 걸림”(−3) | “청소시간 절반”(+3) |
| Effort | 추가 행동·설정 수고·유지관리 부담 | “걸레 빠는 것 지쳐요”(−3) | “신경 쓸 필요 없음”(+5) |

점검 포인트 - Success는 실제 사용 근거가 원문에 있을 때만. 관찰·전언·일반 평판은 0(R1) - 경쟁사 부정 경험은 음수 그대로 유지한다(R6) - 강한 부정 신호를 0으로 방치했거나, 프로모션·링크 문의를 과잉 상향했는지 - evidence 없이 점수만 있는 축은 근거 결손 (Round 1에서는 위반 0건 — 정상) - 【v4.1】 조건절 발화의 감성 부호(R16). “~만 없으면 좋은 제품”은 우려가 핵심이므로 tee_emotion이 양수면 오류다

[Gate 1] 결핍 서술이 있는가?   atomic에 부정적 경험·결핍·제약·우려가 서술되어 있는가?   → 없으면 rootcause_* = N/A, score = 0 (종료)   ■ 배제 목록     · 순수 정보 요청  — "먼지통은 어떻게 비우나요?"     · 순수 긍정      — "잘 작동하는 것처럼 보였습니다"     · 구매 의사 표현  — "나 이제 살 때가 된 거 같다"     · 근거 없는 단답  — "200", "2cm"   ■ 예외 (중요) — 문의문이라도 결핍이 함께 서술되면 통과     · "온수 물걸레가 없어서 스팀으로 대체하고 싶어요" → 결핍 서술 있음 → 통과[Gate 2] 결핍이 제품·서비스에 귀속되는가?   ✅ 통과 → RC 산출 + entity_role 라우팅        · product_brand / unknown  → 자사 개선 트랙        · competitor_brand         → RC 산출하되 자사 우선순위 집계에서 제외,                                      경쟁사 트랙으로 별도 집계  ← 배제가 아니라 분리   ❌ 탈락 → N/A        · 리뷰어·채널 비판(creator_channel)        · 운영성 이슈(링크·프로모션) — R10        · 화자 개인 사정(예산 없음, 이사 예정 등)[Gate 3] maturity 판정 (L1 / L2 / L3)   구체 대상·원인이 원문에 없으면 하향(R7)
Round 1 실측 — 문의 행 130건 중 67건, 긍정 행 중 38건이 RC≥3이었다. 3-게이트 적용 시 217건 중 90~105건이 N/A로 내려간다. rc_coverage·priority_score가 전면 재계산된다.
예외 조항의 실제 적용 예 (v4.1 신설 예문)
원문: “1. 특정 방이나 원하는 구역 전체를 스팀으로 청소할 수 있는 기능이 있나요? 온수 물걸레가 없어서 스팀으로 대체하고 싶어요.”

| 필드 | 산출값 | 정답 | 사유 |
|---|---|---|---|
| inquiry_flag / type | Y / feature_spec | 유지 | 사양 문의 맞음 |
| need_signal | Y / feature_need | 유지 | 기능 요구 |
| rootcause_problem | 스팀 청소 기능 부족 | 온수 물걸레 미탑재 | 결핍 서술을 그대로 |
| rootcause_cause | (있음) | 없음 | 원문에 원인 서술 없음 |
| rootcause_score | 5 (L3) | 3 (L2) | R7 |

→ 이 행의 오류는 “RC가 있다”가 아니라 “L3까지 올려 잡았다”였다. 문의문이라고 무조건 N/A로 내리면 진짜 니즈가 사라진다.

### 7.9 status / scope_exclusion_reason / review_required / proposal_flag

【v4.6 개정】 판정 순서 — **대상을 먼저 정하고, 그다음 내용을 본다**

```
⓪  이 발화의 대상이 무엇인가?          ★ v4.6 신설. 가장 먼저 묻는다

      대상 제품군의 제품              →  ①로 간다
      채널 · 콘텐츠 · 출연자뿐         →  ④  channel_feedback / channel_request
      제품이지만 대상 제품군 밖        →  ④  out_of_scope_product
      대상을 알 수 없다 (대댓글 단독)   →  ④  unresolvable_reply
      정제 후 내용이 없다             →  ④  empty

①  제품에 대한 실질 내용이 있는가? (택소노미 v0.7 §6 근거 어휘 ≥ 1)
      Yes → topic = 캐노니컬 라벨          No → ②

      Yes → topic = "미분류"               No → ③
③  니즈 신호 또는 감성 신호가 있는가?
      Yes → topic = "N/A"  (모수 포함, topic 집계에서만 제외)
      No  → ④  no_analytic_value
④  status = scope_excluded + scope_exclusion_reason
```

**⓪를 건너뛰면 새는 곳** — ③은 감성 신호만 보고 대상을 안 본다.

⓪를 먼저 물으면 ④로 간다. 이것이 v4.5 까지의 누수 경로였다.

### 7.10 confidence_* — 신뢰도

【v4.1 확정】 산정식

| 레벨 | 조건 |
|---|---|
| Low | Topic 없음 |
| Medium | Topic 존재 |
| High | Topic + TEE 존재 |
| Very High | Topic + TEE + Root Cause 완성 |

이 값은 엔진이 후처리로 계산해 강제한다. LLM이 출력한 confidence는 사용하지 않는다.
Round 1에서 확인된 사실: 엔진의 confidence_rating에는 산정식이 없었다. 4개 가설을 454행에 전수 대입한 결과 문서식 43.2%, 최고 가설도 74.4%로, 어떤 결정론적 규칙도 맞지 않았다. trace_summary가 전부 LLM runtime judgment 형식이며 Very High가 1.3%(6건)에 그쳤다. Low만 100% 일치한 것은 “Topic 없으면 Low”가 우연히 겹쳤기 때문이다.
단계별 신뢰도는 3단계

| 컬럼 | 허용값 |
|---|---|
| confidence_rating (종합) | Low · Medium · High · Very High (4단계) |
| confidence_topic / _cej / _inquiry / _need_signal / _entity_role / _score | High · Medium · Low (3단계) |
