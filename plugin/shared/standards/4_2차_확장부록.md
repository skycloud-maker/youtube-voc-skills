# 1. 판단의 축 — 이것만 쥐면 된다

개별 사례를 외우지 마라. 아래 넷으로 대부분이 갈린다.

```
(0)    대상이 무엇인가
       제품·서비스 / 채널·콘텐츠·출연자 / 제품군 밖 / 불명

(0)-b  그 경험·평가가 화자 본인의 것인가
       남의 것 · 화면 속의 것 · 상상 속의 것이면 제품 평가가 아니다

(0)-c  발화의 초점이 제품인가 사람들의 반응인가
       제품의 동작·사양·하자·구매 판단이 하나라도 있으면 제품이다
       ★ 간접 신호도 읽는다 — "영상 덕분에 알았다" 는
         제품이 그것을 안 알려줬다는 뜻일 수 있다

R18    본문이 우선이다
       parent 는 맥락을 이해하는 데 쓰고, 라벨의 근거로는 쓰지 않는다
       본문에 제품에 대한 진술이 하나도 없으면 라벨을 붙일 근거가 없다

# 2. 분리 — 주제를 꼽고 그 대목을 발췌한다   【v3.0 · sky 제안으로 전환】

> sky 2026-08-16 — "주제별로 나눠 놓고 원문에서 관련된 내용을 발췌하라 하면
> 충분히 잘할 것이라 생각하는데... 과소분리가 생기는 것도 충분히 잡을 수 있을 것 같은데"

**「어디서 자를지 찾아라」가 아니라 「주제를 꼽고 각 주제의 대목을 발췌하라」다.**

```
(1) 이 원문에 서로 다른 캐노니컬 주제가 몇 개 있는가
(2) 주제마다 그 주제를 말하는 대목을 원문에서 발췌한다
(3) 발췌에는 그 주제에 대한 반응·평가까지 넣는다
(4) 어느 주제에도 안 들어간 나머지가 voc_residual 이다
```

**이 방식의 이점**

```
발췌이므로 부분문자열(L-1)이 저절로 지켜진다
주제가 둘이면 발췌도 둘 — 과소분리가 구조적으로 안 생긴다
인과·귀결은 자연히 한 덩어리로 발췌된다
```

**★★ 조각마다 원문에서 「서로 다른 대목」 을 잡는다**   【v3.2 · CP-40】

```
같은 대목에 라벨만 바꿔 다는 것은 분리가 아니다.
한 대목에 주제가 둘로 읽히면 나누지 않는다 (§2.1)

실측 — labelC01 에서 Codex 가 조각 28개를 전부 원문 통째로 복사했다
       "역시 가전제품은 LG ㅠㅠ 찜콩할게요"
         조각1  (원문 전체)  제조사 신뢰/품질
         조각2  (원문 전체)  구매의사/이탈
       Claude Code 는 같은 프롬프트로 27조각 전부 실제 발췌했다
★ 내가 §2.2 를 쓰면서 「주제 부분은 서로 달라야 한다」 를 안 적어서 갈렸다
★ check_lineage L-4 도 「동일」 은 못 잡고 있었다. 둘 다 고쳤다
```

## 2.1 주제가 하나면 나누지 않는다

```
★ 「라벨이 다르다」 는 나누기 위한 필요조건이지 충분조건이 아니다
  한쪽이 다른 쪽의 근거·결과·조건·양보이면 하나의 VoC 다

판별   조각을 각각 따로 읽었을 때 그 자체로 VoC 가 되는가
       되면 나눈다. 안 되면 나누지 않는다

★ 접속사가 있다고 안 나누는 것이 아니다
  "소음이 크고, 앱 연동도 안 됨" — 둘 다 단독으로 성립한다. 나눈다
```

## 2.2 반응이 하나면 두 조각에 다 넣는다   【sky 결정 2026-08-16】

```
"세탁도 안 되고 건조도 안 돼서 진짜 짜증나요"
  조각1  세탁도 안 되고 ... 진짜 짜증나요     세탁 성능
  조각2  건조도 안 돼서 진짜 짜증나요          건조 성능

★ "진짜 짜증나요" 가 양쪽에 다 있어야 각 조각이 온전한 VoC 다
  그래서 조각의 합이 원문보다 길 수 있다. 그것은 결함이 아니다
```

## 2.2-1 과분리 병합 — 나누는 것만 보지 말고 합칠 것도 본다   【v3.4 · CP-45】

> sky 2026-08-18 — "불필요한 과분리는 삭제해서 기존 행에 덧붙이는 작업이 되어야 합니다"

```

## 2.3 계보 계약 — `check_lineage.py` 가 검사한다

```

     ★ 없으면 「없던 것이 만들어진」 것이다. 가장 무거운 결함

     그러면 그 조각은 아무것도 더 말하지 않으므로 나눌 근거가 없다

# 3. 라벨을 붙일 수 없을 때

## 3.1 세 갈래로 가른다

```
제품·서비스 얘기가 아니다      status=scope_excluded + scope_exclusion_reason
                             ★ 짝필드다. 둘을 함께 내지 않으면 게이트가 반려한다
                             ★ status 는 source 단위다. 형제 전체에 걸린다
                             ★ 「분석 안 함」 이 아니라 품질 지표 분모에서 빼는 장치다

제품 얘기인데 담을 라벨이 없다   topic=기타 · rationale 에 무엇에 대한 얘기인지 남긴다
                             finding verdict=오류 · 행 verdict=기준서 미커버
                             ★ 두 층은 다르다 (§5.1). finding 이 오류여야 값이 반영된다
                             ★ 재검토로 올리지 않는다. 판독은 끝난 것이다

내용이 불분명하다             topic=미분류
```

## 3.2 「기타」의 뜻   【v3.0 · sky 정정】

```
라벨 있음   집계 가능 · 개선과제가 된다
기타        ★ 기타 라벨 자체는 집계 단위다. "기타 30건" 은 셀 수 있다
            그 안의 개별 의견들이 아직 집계 단위가 못 되는 것이다
            ★ 개별 행은 개선과제가 될 수 있다 — rationale 과 RootCause 가 있으면
            같은 것이 쌓이면 라벨을 신설한다
미분류      판정 실패 — 무슨 얘긴지 모른다
```

★ 1차 캐노니컬은 `기타(로봇청소기)` 처럼 제품군을 달고 있으나 제품군은
`product_category` 컬럼에 이미 있다. **2차는 `기타` 하나를 쓴다**.
★ v3.1 에서 사이드카에 실제로 넣었다 — 그 전에는 문서만 그렇게 적혀 있고
  게이트 허용값에 없어서 내면 Enum 반려였다 (Claude Code 지적).
★ 1차 라벨 4종은 `건조기`·`기타` 제품군을 못 덮는다 (296행).

## 3.3 「제품 전반」은 최후 라벨이다

구체 대상(가격·배송·설치·디자인·용량·성능·앱·서비스)이 있으면 그 라벨을 먼저 쓴다.
구체 대상 없이 제품 전체에 대한 만족·불만이 명확할 때만 쓴다.
★ sky 가 46행을 검수해 76%가 적정이었다. 남용은 아니다.

## 3.4 「사업 신호」 — 버리지 않고 표시해 둔다

VoC 는 아닌데 사업 판단에 쓸 수 있는 층이 있다.

```
값       scope_exclusion_reason = business_signal   (2차 사이드카)
적용     ★ 담을 라벨이 아예 없는 신호에만 쓴다
         라벨이 있는데 제외로 보내면 그것이 더 이상하다
경계     지금 무엇에 쓸 수 있는지 한 줄로 말할 수 있을 때만 쓴다
```

## 3.5 구매 의향은 긍정도 라벨이 있다

`구매의사/이탈` 은 이름과 달리 정의가 이탈만 덮고 있었다.
**2차는 긍정 의사도 이 라벨로 본다** — "무조건 삽니다" · "오늘 결제하고 오는 길".
표시명은 **구매의사** 로 한다 (값은 1차 Enum 이라 동결).

## 3.6 소리 — 두 축을 가른다   【v3.1 · sky 결정 2026-08-16 · 라벨 신설】

```
소음/진동     원하지 않는데 나는 소리 — 모터 · 배수 · 진동
알림·사운드   ★ 신설. 제품이 의도적으로 내는 소리 — 종료음 · 멜로디 · 알람 · 버튼음
              2차 사이드카 (s9_group/secondary_topics.json) · topic_group = 사용성
```

**★ 라벨이 붙는 것과 아닌 것 — 물을 것은 하나다**

> sky 2026-08-16 — "이 내용 자체가 종료음에 대한 불만이나 개선 의견을
> 담는 것은 아니기에 저는 제외로 했지만"

```
물을 것   이 발화가 제품에 대해 무엇을 알려주는가
          ① 소리의 길이·크기·설정·타이밍에 대한 평가나 요구가 있는가
          ② 그로 인한 실제 불편·만족이 있는가
          ③ 제품 동작 정보(잠금 해제 시점 등)가 있는가
          → 하나라도 있으면 알림·사운드. 없으면 제외
```

## 3.7 해석 여지 — 라벨 너머에 무엇이 있는가   【v3.3 · sky 결정 2026-08-18】

> sky — "라벨이 있다고 해서 다 의미 있는 것이 아니라는 것이죠.
> 우리가 그 라벨의 근거 값을 가지고 어떤 해석할 여지가 열려야
> 그 VoC 는 쓸모가 있다는 의미입니다"

`rootcause_problem` 에 적는다. 없으면 **「없음」** 이라고 적는다.

### ★ 판별은 한 줄이다

```
★ 순서 — 해석 여지를 라벨보다 먼저 쓴다 (v3.5 · CP-47)
  라벨을 먼저 정하면 해석을 라벨에서 도출하게 된다. 실측으로 확인됐다

이 원문을 읽고 실무자가 새로 알게 되는 것이 있는가
  있다   → 그것을 한 줄로 적는다
  없다   → 「없음」

★★ 판별은 둘이다. 둘 다 통과해야 여지다
  ㉠ 원문을 정리해 옮긴 것이 아닌가
  ㉡ 이 문장이 이 원문에서만 나올 수 있는 문장인가
     다른 원문에 그대로 갖다 붙일 수 있으면 여지가 아니다
```

### ㉡ 은 왜 필요했나 — 실측

```
한 판독자의 rootcause 1,040개 중 고유 문장이 163개(16%)뿐이었다

   60회  "경쟁 대안과 비교할 때 제품 전반이 선택 기준 또는 이탈 요인으로 작동한다."
   53회  "경쟁 대안과 비교할 때 제조사 신뢰/품질이 선택 기준 또는 이탈 요인으로 작동한다."
   40회  "설치/설치 편의성 정보가 사전에 충분히 전달되지 않아 판단에 공백이 있다."
   ★ 라벨 이름만 갈아 끼운 한 틀이다. 조사도 맞지 않았다("가성비이")

㉠ 만으로는 안 걸린다 — 원문 재진술이 아니기 때문이다
㉡ 에 걸린다 — 60개 원문에서 똑같이 나온 문장이다

### 왜 이 기준인가 — 두 대안을 실물로 대봤다

```
원문   "저도 애벌 세척을 해서 그런지 다행히 그런 증상은 없네요"
라벨   위생/살균

  느슨한 기준   "애벌세척하면 증상이 없다"        → 여지 있음
                ★ 원문을 정리해 옮긴 것이다. 라벨을 알면 새로 알 게 없다
                  이 기준으로는 거의 모든 행이 「쓸모 있다」 가 된다
                  그러면 이 축을 세운 이유가 없어진다

  ★ 채택한 기준  라벨(위생/살균)에 「증상 없음」 을 더한 것뿐이다  → 여지 없음
```

```
원문   "빈통 채로 식초랑 소다 놓고 퀵세척 한번 하면 냄새 싹 빠져요~"
라벨   위생/살균

  ★ 여지 있음 — "냄새 해소가 제품 기능이 아니라 사용자 요령에 의존한다"
    라벨만으로는 알 수 없다. 「제품이 스스로 해결하지 못한다」 가 새로 드러난다
```

### 갈리기 쉬운 곳

```
만족 사례       "잘 쓰고 있어요" 만 있으면 없음
                "이래서 잘 쓴다" 는 이유가 있으면 있음
사용자 요령      ★ 대개 있음 — 제품이 안 해주니 사람이 하는 것이다
경쟁사 비교      ★ 대개 있음 — 자사가 어디서 밀리는지가 나온다
질문·문의        묻는다는 것 자체가 「안 알려줬다」 는 뜻일 때가 있다.
                그 각도가 보이면 있음, 단순 호기심이면 없음

★ 억지로 만들어 쓰지 마라. 「없음」 은 실패가 아니라 정확한 판정이다
★ 반대로 「원문 재진술」 을 여지로 쓰지 마라. 그건 요약문(atomic_voc_summary) 자리다
```

### 요약문과 다르다

```
atomic_voc_summary   이 조각이 무슨 말인가        "식초·소다로 냄새를 뺀다"

```
